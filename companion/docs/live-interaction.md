# 直播弹幕接入与回应

更新：2026-11-02。本文记录本轮实现的边界和后续验收要求，不代表已经完成商业上线验收。

## 先调研，再选机制

- [AI-Vtuber 的消息处理源码](https://github.com/Ikaros-521/AI-Vtuber/blob/main/utils/my_handle.py)：有独立的消息去重数据、周期任务、念弹幕、答谢以及音频队列操作。借鉴分阶段处理与答谢节流；不直接复制它的业务代码。
- [Open-LLM-VTuber 的 B 站适配器](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/main/src/open_llm_vtuber/live/bilibili_live.py)：通过平台接口和消息回调向上游传输，维护连接和会话状态。借鉴平台与对话边界。
- [Streamer.bot Actions](https://docs.streamer.bot/guide/core/actions)：动作放在队列里，Blocking 控制串行执行。借鉴单一播报通道；生成完成不能等同于播放完成。
- [Twitch EventSub](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/) 与 [消息定义](https://dev.twitch.tv/docs/eventsub/websocket-reference/)：心跳、重连、订阅撤销以及重投消息 ID 都是接入协议的一部分。作为可靠性检查依据，本轮没有新增 Twitch 接入。
- [Neuro-sama 观众研究](https://arxiv.org/abs/2509.10427)：质性研究强调共同创作、持续人设与集体情绪事件。由此提出的产品判断是：要让观众影响直播走向，而不是把每条弹幕变成问答。该研究不披露 Neuro-sama 的内部实现，不能据此声称复刻了其算法。

## 模块边界

接入：`bili/` 管 B 站开放平台连接；`douyin/` 管网页直播间监听、推送解包、验签和收件箱。接入层不调用模型，不负责选题。抖音收件箱通过 `subscribe()` 对外发布，支持独立录制器或其他消费者；单个消费者抛错不会阻止其他消费者，异常会计数并记录日志。装配发生在路由中，业务适配发生在 `bridge.py`，收件箱内部不导入主持。

接收边界：`intake.py` 复制并归一化 LiveEvent，以平台和消息 ID 去重。主持的观众统计、愿望与弹幕板在去重之后更新，避免重连重投重复记账。无 ID 事件的推断去重目前由抖音收件箱承担。

处理：`queue.py` 管容量、时效和排队；`selection.py` 管低成本注意力策略；`director.py` 管上下文和文本生成；`host.py` 管节目、轮次与播放反馈。处理层接受 LiveEvent，离线测试不需要连接真实平台。

舞台：`session.ts` 将选好的轮次送入现有表演和语音系统，通过已有 playbackTicket / playbackResult 等待结果，再提交 ack。网络失败时保留 ack，在后续轮询重试。

## 本轮实际行为

- 新配置普通弹幕聚合窗口默认 4 秒，原来保存的窗口值仍然保留；可在控制台调到 1–120 秒。它是选题窗口，不是实测端到端响应延迟。
- 候选按疑问特征、正文长度、相同内容的不同观众数、等待时间与最近选择过的观众排序，每轮最多取三个不同内容、不同观众的代表；生成提示要求重点接一个话题。
- 相同内容经过 Unicode、大小写、空格与标点归一化后合并。这不是语义聚类，不会把所有不同措辞的同义问题自动合并。
- 普通弹幕与关注事件超过 45 秒失效，礼物类事件窗口为 300 秒。队列最多 400 条，溢出有计数；礼物洪峰也不会突破容量。
- 连续两轮礼物后，如果已有普通弹幕达到窗口，会先安排一轮普通回应。普通礼物不再带打断标记；舞台忙时不生成叠加播报。
- 最近四轮成功播放或仅文字展示的观众消息和回应进入上下文。失败、被打断的回应不当作已说过；播放失败可在控制台查看。
- 同时只允许一个生成任务；停播或重新开播后，旧任务结果不能发布。轮次 ID 带进程实例标识，避免后台重启后与前端已播 ID 碰撞。
- 模型请求不再对每个端点立即重试两次；主模型一次、备用模型一次。单次 HTTP 读超时 8 秒、连接超时 3 秒；这不是整个生成链路的硬性总时限。
- 弹幕以 JSON 数据提供给模型，系统提示明确其不可信。该措施降低角色混淆风险，但不是完整的模型输出审核机制。
- 抖音直播控制台可直接输入房间链接并启动监听，接收开关与主持开播独立。开放平台回调缺密钥返回 503，验签失败返回 401，配置的来源房间不匹配返回 403。

## 离线验证

在仓库根目录运行：

```powershell
.\companion\backend\.venv\Scripts\python.exe -m pytest companion/backend/tests/test_live_host.py companion/backend/tests/test_live_douyin.py companion/backend/tests/test_live_attention.py -q -p no:cacheprovider
```

27 项测试覆盖已有平台包解析、签名、开播约束、预算、动作与点歌，以及新增的重复事件副作用、100 条刷屏聚合、450 条礼物容量、付费事件与普通弹幕调度、播放反馈、生成中停播、上下文格式、消费者异常隔离和回调密钥/签名/房间校验。

前端执行 `npm run build`。构建通过；Vite 仍提示部分资源路径在运行时解析、模块同时静态/动态导入与大体积 chunk。构建通过不代表浏览器视觉和真实音频验收通过。

额外执行 `tsc --noEmit`，全仓检查未通过，报错涉及 lipsync、codewatch、mocap 的 Vue 声明、performance、tarot、stt 和 main 的 Vue 声明；没有报本轮直播 TS 模块错误。这些其他模块的类型问题不在本轮修改范围内。

## 商业上线前仍必须完成

1. 用目标平台真实房间和真实模型、语音引擎验证完整链路；这轮没有测得真实连接成功率、首个可听音频延迟或自然度评分。网页抓取依赖平台页面与浏览器实现，不能当作已经获得 SLA 的官方服务。
2. 付费事件目前仍为内存队列，溢出或进程重启会丢失，订阅失败也未实现持久重投。正式收费前需要持久接收记录、消费游标、失败重试与人工补偿界面。
3. 本轮只有确定性注意力规则，尚无语义话题聚类、跨场观众记忆、直播画面/游戏状态理解。需要真实弹幕录制与人工评分集，比较复读率、接话相关性、人设一致性、对话延续与普通观众覆盖率。
4. 要补完整输出审核与人工接管。已补停止播放联动和多窗口播报独占领取，但当前仍使用进程内单主持，不能直接部署为多租户服务。
5. 建议验收目标（不是当前实测结果）：连续 8 小时运行；平台重连和模型故障注入；10/100/1000 条每秒输入回放；确认无并行播报、无重复付费履约；记录从接收、选中、生成、合成到播放结束各阶段 p50/p95 与真实费用。

后续已交付独立彩排环境，包含虚构弹幕源、真实/替身模型、正式语音与 3D 舞台、故障演练、持久收据和失败礼物补播。启动与已完成的实测见 [直播彩排交付](live-lab.md)。
