# MiniCPM-V 4.7 1B · 录屏看画面

本地测试：连续截这台电脑的屏幕，让 `openbmb/MiniCPM-V-4.7-1B` 看画面里是什么。

和上一级的 MiniCPM-o 4.5 **不要共用虚拟环境**。o 4.5 钉死 `transformers==4.51`，V 4.7 要 `transformers>=5.18`。这里用自己的 `v47\.venv`。

权重下到 `minicpm-o-demo\models\MiniCPM-V-4.7-1B`（ModelScope 优先，失败再走 hf-mirror）。

## 安装

```powershell
cd minicpm-o-demo\v47
.\setup.ps1
```

## 启动

先腾出显存（关掉 xiaoke 主窗口，或者正在跑的 o 4.5）。1B 本身不大，但别和别的模型抢卡。

```powershell
cd minicpm-o-demo\v47
.\start.ps1
```

浏览器打开 http://127.0.0.1:8766 ，点「开始看屏幕」。

- 默认主屏幕连续录屏，2 FPS、最近 4 秒滑动窗口、长边 960、`16x`、回复上限 32 token。可选 1/2/4/6 FPS。
- 录屏线程在模型推理时始终继续采集。窗口不是一段录完再停：每次推理都从持续更新的流中取最新几秒。间隔填 0 表示达到场景节流后立即理解最新窗口。
- 无论静止还是运动，开始按钮都使用原生视频输入，不退回单图。直接在内存中组帧并传采集时间戳，不写 MP4。
- 页面显示实际采样率、输入帧数、结果距画面的秒数和跳过帧数。采集 FPS 不等于每秒能完成的理解次数。
- 只保留最近一个窗口。模型太慢时会跳过过期帧，页面如实计数，不积压旧视频。停止按钮同时停止理解与录屏。
- 首次说明主要内容，后续只报告关键事件或状态变化；不逐段填写标题、字幕和微动作。历史提示只带上一条观察。
- 标题含 `MiniCPM-V 4.7` 的识别窗口在模型输入中自动遮黑，防止模型读取自己的预览和历史输出。
- `/api/observations?limit=100` 可查看最近的模型原始输出、是否被去重、实际提示词、场景切换、静态画面跳过及错误；内存保留 2,000 条，且每个服务会话追加写入 `logs/live-video-日期.jsonl`。测试期会无损保存每一张连续原始屏幕帧（`*-raw/`）和每次实际送进 MiniCPM 的处理后帧序列（`*-model-input/`）；JSONL 的 `raw_frames`、`model_frames` 精确关联窗口，配合帧序号、时间跨度和参数即可复现模型输入。不会另行编码为 MP4，因此不会把重叠窗口再次压制成失真的“视频”。

### 场景识别与热切换

页面提供自动，以及与原有识别系统一致的五种策略：游戏、音乐、电影/剧集、短视频、工作/普通屏幕。它们分别关注对局阶段和关键局势、明确的播放信息、当前情节、信息流中的独立视频，或任务状态。运行中直接选择场景并点「应用当前场景」：录屏和模型不重启，下一段按新策略识别，旧场景的文字记忆会清空，避免把游戏观察带入视频。

为避免重复解释同一段画面，连续视频不会对每一张新帧都重跑推理。它会等到当前场景的最小间隔后再取最新窗口：游戏 3 秒、自动 4 秒、短视频/工作 5 秒、电影/音乐 10 秒；静止画面则跳过。
- 只绑 `127.0.0.1`。截图和描述不出这台机器。

环境变量 `MINICPM_V47_MODEL` 可以指向已经下好的权重目录。

## 原生视频输入实验

实时录屏页面现在始终使用原生视频，上面的开始按钮无需环境变量。
以下环境变量仅用于小可爱 `/api/glance` 多图请求的旧接口对照：

在当前 PowerShell 中设置后启动眼睛进程（已经启动的进程需要重启）：

```powershell
$env:MINICPM_V47_INPUT_MODE = "video"
.\start.ps1
```

多帧请求会最多选 6 帧、按 2 FPS 编成临时短片，再经 PyAV 解码进入
V 4.7 的原生视频处理器；临时文件在推理后删除。单帧请求保持单图。
不设置此变量时保留原有多图输入，方便对照。这里的 2 FPS 是组片时间轴，
还没有传递屏幕采集的实际时间戳，不能用于判断真实动作速度。

用同一组按时间排列的已存截图测试三条路径，不会重新截屏：

```powershell
.\.venv\Scripts\python.exe benchmark_video.py tmp/reel-1.jpg tmp/reel-2.jpg tmp/reel-3.jpg tmp/reel-4.jpg --output tmp/video-benchmark.json
```

默认重复两轮并反转执行顺序，记录模型原始回答、输入 token、视频实际处理帧数、
预处理/生成耗时和 PyTorch 峰值显存。显存数字不含桌面或其他进程，
reserved 数字受前次推理缓存影响。单图基线只取最后一帧；多图与视频使用同一批帧，
视频另有有损编码，因此这是工程路径对照，不是严格的模型精度评测。
质量判断还需要有人工标注的界面切换样本，不能只看回答是否流畅。

“6 张 448×448 帧压成 64 token”是 MiniCPM-V 4.5 的 3D-Resampler 说明，
不能直接当作 V 4.7 的资源预算。4.7 使用自己的视觉压缩和时空位置机制，
应以本脚本记录的实际 token 数为准。
